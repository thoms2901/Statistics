From wallet seed to Ethereum address

October 2026

An Ethereum wallet turns twelve or twenty-four words into an address through a chain of separate standards. Here I compute each step in the browser and examine the entropy of the seed, the effect of hashing on public keys and the error detection provided by the EIP-55 checksum.

1. The pipeline

mnemonic (12/24 words) | BIP-39: PBKDF2-HMAC-SHA512, 2048 rounds, salt "mnemonic"+passphrase seed (512 bit) | BIP-32: HMAC-SHA512("Bitcoin seed", seed), then child derivation | BIP-44: path m/44'/60'/0'/0/0 private key k (256 bit integer, 1 ≤ k < n) | secp256k1: Q = kG public key Q = (x, y) | Keccak-256(x || y), keep the last 20 bytes address (160 bit, 40 hex chars) | EIP-55: upper/lower case driven by Keccak-256 of the hex text checksummed address

Running it

The default phrase is the public BIP-39 test vector. Do not type a real recovery phrase into any web page, this one included.

Check: with the test phrase, empty passphrase and the default path, the result must be 0x9858EfFD232B4033E47d90003D41EC34EcaEda94, the address published as reference for this phrase by wallet libraries. My implementation gives the same, which also confirms the Keccak code below. Changing the last index of the path (0 → 1, 2, …) gives the next accounts, which is what MetaMask does when you press "add account".

2. Standards used

BIP-39, mnemonic and seed (2013)
Starts from 128 to 256 random bits. A checksum (the first ENT/32 bits of SHA-256 of the entropy) is appended, the result is cut into 11 bit chunks and each chunk picks a word from a list of 2048. The words are only a human-friendly encoding of the entropy. Then PBKDF2 with HMAC-SHA512 and 2048 iterations stretches words plus optional passphrase into a 512 bit seed. The iterations slow down brute force on weak passphrases; they do not add entropy.
BIP-32, hierarchical deterministic keys (2012)
From the seed, HMAC-SHA512 with key "Bitcoin seed" gives a master private key (left 32 bytes) and a chain code (right 32 bytes). Every child key is again HMAC-SHA512 of the parent material plus an index. One backup therefore recovers an unlimited tree of keys. Hardened children (index ≥ 231, written with ') need the parent private key; normal children can be derived from the extended public key, which is how watch-only wallets work.
BIP-44, derivation paths (2014)
A convention on which branch of the BIP-32 tree to use: m / purpose' / coin_type' / account' / change / index. For Ethereum this is m/44'/60'/0'/0/i (60 is Ethereum in SLIP-44). It is the reason the same 12 words open the same accounts in MetaMask, Rabby or a Ledger.
secp256k1, elliptic-curve public-key cryptography
The curve y² = x³ + 7 over a 256 bit prime field (the big version of the toy curve of HW1). The public key is Q = kG. It is the only asymmetric step: it lets the owner sign transactions with ECDSA while everybody else can verify the signature with Q. Recovering k from Q is the elliptic curve discrete logarithm problem.
Keccak-256, address hashing
The 64 bytes x || y of the public key are hashed and the last 20 of the 32 output bytes become the address. The hash makes the identifier shorter, removes the algebraic structure of the point and hides the public key until the first transaction is signed.
EIP-55, checksum by letter case (2016)
The lowercase hex address is hashed again with Keccak-256; every letter a..f whose matching hex digit in the hash is 8 or more is written in uppercase. The 20 bytes do not change, only how they are written, so old software still reads the address while new software can catch typos.

3. Types of operation

kind what it means where in the pipeline
key generation new secret material from a random source the 128 to 256 bits of entropy behind the words
key derivation deterministic new keys from an existing secret, no new randomness PBKDF2 (words → seed), BIP-32/44 (seed → child keys)
public-key cryptography a private/public key pair, easy one way and hard the other, enables signatures secp256k1, k → Q = kG, ECDSA
hashing fixed-size, one-way, collision resistant fingerprint Keccak-256 for the address; SHA-256 for the BIP-39 checksum; SHA-512 inside HMAC
checksum redundancy to detect accidental errors (not attacks) last word of the mnemonic, EIP-55 capitalisation
encoding same information in another alphabet, reversible, no security bits → words, bytes → hex, 0x prefix

The pair that is easiest to confuse is generation and derivation. Only the very first step uses randomness. Everything after it is a deterministic function, which is exactly why a wallet can be restored from words alone, and also why the security of every key in the tree can never be higher than the entropy of those words.

4. Statistical properties

4.1 Entropy budget of BIP-39

The checksum bits are not random: they are a function of the entropy. So a random sequence of 12 words is a valid mnemonic only with probability 2−4 = 1/16, and for 24 words 1/256. The 512 bit seed has at most 128 (or 256) bits of real uncertainty: stretching does not create entropy, it only spreads it. A guessable passphrase adds very little.

4.2 Avalanche effect of Keccak-256

Take a random 64 byte input (the same size as a public key), flip one random bit, hash both and count how many of the 256 output bits differ. For an ideal hash the count should follow a Binomial(256, 1/2): mean 128, standard deviation 8.

4.3 Hashing removes the structure of the public key

In HW1 I found that scalar multiplication is very structured: (k+1)G = kG + G. Here I check the same on the real curve and look at what the hash does to it.

The public keys of k and k+1 are linked by a known addition, anybody can go from one to the other. After Keccak-256 the two addresses differ in about half of their 160 bits and there is no relation left to exploit. This is the division of labour: the curve provides structure (needed for signatures), the hash provides randomness-like behaviour (needed for identifiers).

4.4 EIP-55 checksum

Only letters carry case information. In a random address each of the 40 hex characters is a letter with probability 6/16, so the number of letters is L ~ Binomial(40, 3/8), mean 15. If someone mistypes the case of a random address, the wrong pattern passes the check with probability 2−L, and on average

P(pass) = E[2−L] = (1 − 3/8 + 3/16)40 = (13/16)40 ≈ 0.0247 %

This is larger than 2−15 ≈ 0.0031 % (plugging in the mean) because addresses with few letters are much weaker than average. Below I generate random addresses, apply EIP-55 and count the letters.

An address typed all lowercase or all uppercase is accepted without a check (that is the backward compatibility). Mixed case is verified. Whether a wallet really warns the user is up to the client implementation, the standard does not force it.

5. Chronology

year technology comment
1977 RSA first practical public-key scheme (factoring). Not used in Ethereum, but it opens the idea of key pairs and signatures.
2001 SHA-2 / SHA-512 NIST hash family (FIPS 180-2, final in 2002), Merkle-Damgård design. Used inside HMAC-SHA512 in BIP-32 and PBKDF2 in BIP-39.
2012 BIP-32 HD wallets, one seed for a whole tree of keys (Bitcoin).
2013 BIP-39 mnemonic words for the seed.
2014 BIP-44 standard paths, multi-coin and multi-account. Ethereum chooses Keccak in its yellow paper in the same period.
2015 SHA-3 (FIPS 202) NIST standardises Keccak with a different padding. Ethereum mainnet launches in July 2015 with the original Keccak.
2016 EIP-55 mixed-case checksum, added after launch without changing the address format.

The order explains the design: Ethereum reused what the Bitcoin world already had (secp256k1, BIP-32/39/44) and took Keccak before the SHA-3 standard was final, which is why it ended up with a hash that is not SHA3-256.

6. SHA-2 vs Keccak / SHA-3

SHA-256 and SHA-512 (SHA-2) are built with the Merkle-Damgård construction around a compression function. Keccak is a sponge: a 1600 bit state, a permutation applied 24 rounds per block, the input absorbed into the first part of the state (the rate) and the output squeezed from it. NIST ran the SHA-3 competition (2007 to 2012) precisely to have a design unrelated to SHA-2, and Keccak won.

When FIPS 202 was published, NIST changed the padding: SHA-3 appends the domain separation bits 01 before the usual 10…01 padding, original Keccak does not. In bytes, the first padding byte is 0x06 for SHA3-256 and 0x01 for Keccak-256. Same permutation, same rate, completely different outputs. In Solidity keccak256 always means the original one.

Empty string gives Keccak-256 = c5d24601…5d85a470 and SHA3-256 = a7ffc6f8…80f8434a, the official test values. In my code the only difference between the two functions is that one byte.

7. Role of each technique

Because each step answers a different question, and the properties needed are partly incompatible.

  • BIP-39/32/44, key management. How do I back up and organise many keys with one secret that a person can write on paper? This needs determinism and reproducibility, not hardness.
  • secp256k1, ownership. How do I prove I control an account without revealing the secret? Only a public-key scheme with a hard inverse problem can do that, and it needs algebraic structure (the one seen in HW1) to make signatures verifiable.
  • Keccak-256, identifiers. How do I get a short, fixed-size, collision resistant name from a public key? That is what a hash is for, and it should have no structure at all.
  • EIP-55, human errors. How do I catch a typo before sending money? Cheap redundancy is enough; an adversary is not the threat model here.

One algorithm cannot be at the same time structured (for signatures) and structureless (for hashing), reproducible and unpredictable. Composing small specialised primitives also means each one can be studied and, if needed, replaced on its own.
