From private key to public key on a toy elliptic curve

October 2026

Ethereum derives a public key from a private key with one operation: scalar multiplication on the curve secp256k1, Q = kG. Here I rebuild the same operation on a tiny curve with the same shape, y² = x³ + 7 (mod 17), small enough that every point can be listed and every step checked by hand. After that I repeat the computation for many scalars and base points and look at what the outputs look like statistically.

1. The curve

Same coefficients as secp256k1 (a = 0, b = 7), but the prime is 17 instead of a 256 bit number. Checking all 17×17 pairs gives the affine points below, plus the point at infinity O, which works as the zero of the group.

Two things are visible already. Only 8 of the 17 possible x values appear, because x³ + 7 has to be a square mod 17. And the orders are 2, 3, 6, 9 or 18, all divisors of the group size 18 (Lagrange). The base point suggested in the assignment, G = (1, 5), has order 9, so it generates a subgroup with 8 points plus O.

Point addition

For P = (x1, y1) and R = (x2, y2):

λ = (y2 − y1) · (x2 − x1)−1   if P ≠ R
λ = 3x1² · (2y1)−1   if P = R (doubling)
x3 = λ² − x1 − x2,   y3 = λ(x1 − x3) − y1   (all mod 17)

Division means multiplying by the modular inverse, which I compute with the extended Euclidean algorithm. If x1 = x2 and y1 = −y2, the result is O. Worked example: 2G with G = (1, 5): 2·5 = 10, 10−1 = 12 (since 120 = 7·17 + 1), λ = 3·12 = 36 ≡ 2, x3 = 4 − 2 = 2, y3 = 2(1 − 2) − 5 = −7 ≡ 10. So 2G = (2, 10).

2. Generating the toy key pair

With k = 6 and G = (1, 5) the result is Q = (5, 8). Try k = 15: you get the same Q, because the order of G is 9 and 15 ≡ 6 (mod 9). On secp256k1 the same thing is true in principle, but the order is a 256 bit prime, so it never matters in practice.

4. Statistical exploration

For a base point of order n, every private key k from 1 to n − 1 gives a different point, so I can run the experiment exhaustively instead of sampling. I encode a point as 10 bits: 5 bits for x followed by 5 bits for y (x || y).

Results

Coordinates. The distribution of x is far from uniform over 0..16: nine values never appear at all, because no point has them. With G = (1, 5) each x that appears shows up exactly twice (once for kG and once for (n−k)G = −kG), and y is spread more evenly because −P only changes the sign of y. So any uniformity I see is a consequence of the group structure, not of randomness.

Correlation with the input. Pearson's r between k and x comes out as exactly 0 for every base point. That looks like perfect independence but it is the opposite: x(kG) = x((n−k)G), so x is a symmetric function of k around n/2 and its linear correlation cancels out. A coefficient of zero says nothing about how predictable the output is. The output is in fact completely determined by k.

Bits. The highest bit of each coordinate is almost always 0, because only the value 16 sets it. This is a property of the encoding (5 bits for numbers below 17) more than of the curve.

Avalanche. Flipping one bit of k changes on average a bit more than 4 of the 10 output bits, a little under the 5 of an ideal hash. But there is a stronger structure next to it: (k+1)G = kG + G always. Knowing one public key and G, the "neighbouring" keys are trivial to compute. A hash function is designed so that nothing like that exists.

5. One-way function vs hash function

property k → kG cryptographic hash
deterministic, easy forward yes yes
hard to invert yes, ECDLP (on a real curve) yes, preimage resistance
algebraic structure yes: (a+b)G = aG + bG none by design
uniform looking output not required required
avalanche criterion not required required
collision resistance trivial: k and k+n collide, and that is fine central requirement
used for key pairs, signatures fingerprints, addresses, integrity

For a one-way function used in public-key cryptography the property that matters is hardness of inversion: given Q and G, finding k should be infeasible. That rests on the elliptic curve discrete logarithm problem, which is a structural, number-theoretic statement. The homomorphism (a+b)G = aG + bG is not a weakness, it is exactly what makes ECDSA signatures and key derivation (BIP-32, see HW2) work.

Uniform coordinates, balanced bits, no correlation and the avalanche effect are the tests that make sense for a hash function, whose whole job is to behave like a random function. Applied to kG they mostly show the group structure rather than measure security. On this toy curve inversion is trivial anyway: at most 17 tries recover k.

6. Limits of this experiment

p = 17 gives a group of 18 elements, so the "statistics" are complete enumerations of a few dozen points, not samples. Nothing here says anything about the security of secp256k1, whose prime and group order are around 2256. The code is meant to show the mechanism, it is not constant time and must not be used for real keys.
